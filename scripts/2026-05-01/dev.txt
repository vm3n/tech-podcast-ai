Imagine you're working on a critical system, and you think you've got everything locked down, but then you discover that a simple typo in your code can become a system-wide kill switch. Sounds like a nightmare, right? Well, that's exactly what happened with the uutils project, a Rust reimplementation of the GNU coreutils. Recently, Canonical disclosed 44 CVEs in uutils, and what's interesting is that none of these bugs were caught by Rust's borrow checker or other safety features. 

So, what happened here? The largest cluster of bugs in the audit was related to a problem called Time Of Check To Time Of Use, or TOCTOU. This is when you do one syscall to check something about a path, and then another syscall to act on the same path. The problem is that between those two calls, an attacker can swap the path component for a symbolic link, and the kernel will re-resolve the path from scratch on the second call. Think of it this way: you're checking if a door is locked, and then you're trying to open it, but between those two actions, someone can switch the door with a fake one.

Rust's standard library makes this easy to get wrong, because the ergonomic APIs you reach for first all take a path and re-resolve it every time, rather than taking a file descriptor and operating relative to that. For example, if you're using the `fs::metadata` or `File::create` functions, they'll re-resolve the path every time, which can lead to TOCTOU bugs. To avoid this, you need to anchor your operations on a file descriptor instead of a path. 

Let's look at a specific example. There was a bug in the `install` function where it would clear the destination, and then create the destination. But between those two calls, an attacker could plant a symlink, and the `File::create` function would follow the symlink and overwrite the target file. The fix was to use `OpenOptions::create_new(true)` instead, which guarantees that the file is new and doesn't exist before. 

Here's the thing: Rust's safety features are great, but they're not a silver bullet. You still need to be careful when writing systems code, especially when dealing with paths and syscalls. So, what can you do to avoid these kinds of bugs? The first rule is to anchor on a file descriptor instead of a path. This means using functions like `openat` or `fstatat` instead of `open` or `stat`. 

Another important rule is to set permissions at creation time, not after. This means using `OpenOptions::mode()` or `DirBuilderExt::mode()` to set the permissions when you create a file or directory, rather than trying to change them later with `fs::set_permissions`. And here's why that's a big deal: if you create a file with default permissions and then try to change them, there's a brief window where the file exists with the default permissions, and an attacker could exploit that. 

There are also issues with string equality on paths. For example, if you're checking if a path is the root directory, you can't just compare it to `/` using string comparison. You need to use `fs::canonicalize` to resolve the path to its canonical form, and then compare it. This is because a path like `/../` or `/./` can be equivalent to `/`, but a simple string comparison won't catch that. 

And then there's the issue of staying in bytes at Unix boundaries. Rust's `String` and `&str` are always UTF-8, but Unix paths and environment variables can contain arbitrary bytes. If you're not careful, you can end up with data corruption or security vulnerabilities. For example, if you're using `from_utf8_lossy` to convert a byte slice to a string, you can silently corrupt the data if it's not valid UTF-8. 

The audit also found bugs related to panics and error handling. For example, if you're using `unwrap` or `expect` to handle errors, you can end up with a denial of service vulnerability if an attacker can trigger a panic. Instead, you should use `?` or `get` to handle errors properly, and surface a real error to the user. 

And finally, there's the issue of bug-for-bug compatibility. If you're reimplementing a battle-tested tool, you need to make sure you're matching the original tool's behavior exactly, including its bugs. This is because shell scripts and other code may rely on the original behavior, and if you change it, you can introduce security vulnerabilities.
