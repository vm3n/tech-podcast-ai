Imagine you're sleeping, and an AI agent is booking a flight, querying a ledger, and triggering a payment on your behalf. Sounds convenient, right? But here's the thing, the way the internet handles authentication and authorization, it's not designed for this kind of scenario. The current system, OAuth 2.0, has been working well enough for humans logging into apps, but when it comes to AI agents making decisions and taking actions on our behalf, it starts to show its seams.

Think of it this way, when you log into Salesforce via Google, the flow is synchronous - you get redirected, you consent, and a token is issued. But when an AI agent is doing something, there's no consent screen, no moment where you explicitly say yes. The agent is making decisions, calling services it discovered at runtime, and maybe even handing off to sub-agents. OAuth wasn't designed to track any of that.

The spec was written back in 2012 by Dick Hardt, and it was designed for clients that are known at build time. But agents pick their tool chain at runtime, one call at a time, choosing the next tool as the task unfolds. A scope like mail.read looks identical whether the agent is summarizing your inbox or exfiltrating it. The protocol can't tell them apart.

This is the problem the industry is currently trying to solve. And it's a big deal, because we're talking about AI agents that can take actions on our behalf, and we need to make sure that they're doing what we want them to do, and not something else. So what's being done about it?

Well, there are a few initiatives underway. Anthropic's Model Context Protocol, or MCP, gives agents a standard interface to tools and data sources. And MCP's March 2025 specification standardized authorization using OAuth 2.1, requiring PKCE from all clients and adding metadata discovery and dynamic client registration. But one gap in that flow is discovery - an agent hitting a remote MCP server for the first time needs to know where the authorization server lives before it can start any OAuth exchange.

And then there's A2A, or Agent-to-Agent, which was published by Google in April 2025. A2A handles the connection between agents themselves, using Agent Cards to publish capabilities and OAuth 2.0 flows to handle authentication. It's built on existing web infrastructure standards, making it compatible with systems businesses already run.

But here's the thing, both MCP's OAuth 2.1 and A2A's authentication schemes still rely on bearer tokens. And in a multi-agent pipeline, that creates a structural problem. If you hold the token, you can use it. But in a multi-hop chain, you need to make sure that each hop can only reduce permissions, never expand them. And that's where AAuth comes in - a new specification that treats agents as first-class identities, bringing together authentication and authorization built on OAuth RFCs, with message signing and discovery.

So what does this mean for you, as a software developer? Well, if you're building integrations that agents will traverse, you need to think about whether your auth layer can handle delegated credentials and produce a verifiable trail of which agent did what and on whose behalf. Most existing OAuth implementations weren't designed to answer that. But the work to make them do so is happening now, and the teams that engage with it early will be ahead of the ones waiting for a finished spec.

Ready to get started? You should be, because the future of authentication and authorization is being written right now, and you don't want to be left behind.
